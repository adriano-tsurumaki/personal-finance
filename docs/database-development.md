# Database development and migrations

The schema is defined in `src/main/db/schema.ts`. Drizzle ORM handles queries,
validation lookups, seed inserts, and transactions. `better-sqlite3` remains its
synchronous SQLite driver; application services do not use raw driver queries.

## Local development

Copy `.env.example` to `.env` if needed:

```dotenv
DB_FILE_NAME=./personal_finance.db
```

The path is resolved relative to the project root by both the app and Drizzle Kit.
A local `file:` prefix is also accepted. The database and SQLite sidecar files are
ignored by Git. Development no longer opens the database in Electron's user-data
directory. Existing files there are left untouched.

```sh
pnpm db:migrate
pnpm dev
```

`db:migrate` creates the database and applies pending migrations without opening
the UI. The app also applies pending migrations before registering IPC handlers.
Startup does not create a prototype user. Local profiles are created through the
profile screen; creating or entering a profile initializes its default categories
and the shared payment-method catalog atomically. Stable catalog keys prevent
repeat initialization from duplicating defaults or overwriting customized names,
colors, or archived categories. Existing prototype profiles remain selectable.
Use `pnpm db:studio` to inspect the local database.

## Changing the schema

1. Edit `src/main/db/schema.ts`.
2. Run `pnpm db:generate --name=describe_change`.
3. Review the generated SQL and snapshot in the new timestamped `drizzle/` folder.
4. Run `pnpm db:migrate` and `pnpm test:db`.
5. Commit the schema and generated migration folder together.

For data-only changes, use `pnpm db:generate --custom --name=describe_data_change`
and write the SQL into the generated migration. Do not edit migrations that have
already been applied or use `push` in place of the versioned workflow. Back up
valuable databases before applying structural changes.

Drizzle records applied migrations in `__drizzle_migrations`; restarting does not
reapply them. Failed migrations roll back. SQL and snapshots use the timestamped
folder format generated by the installed Drizzle Kit 1.0 release candidate.

Category uniqueness uses the deterministic `category_name_key` SQLite function,
registered by `initDb`. External writers must register the same NFC/Unicode
lowercase function before writing categories; SQLite tools without it can read
the database but cannot maintain the expression index. Use application services
for category changes. Legacy category names that conflict under this comparison
must be corrected before migration; no names or associations are silently changed.
The category migration adds columns in place to preserve foreign-key references.

## Existing databases

The initial migration deliberately uses `CREATE TABLE IF NOT EXISTS` so that it
can also adopt the schema produced by the previous application initializer,
including its `categories.icon_key` upgrade. Existing rows, IDs, cents, dates,
foreign keys, and constraints are preserved. This baseline is only for that
known schema, not arbitrary SQLite databases or the earlier unused draft schema.
Older databases without `icon_key` must first receive the previous application's
upgrade. Future structure changes must be separate migrations.

To use an existing development database, copy it while the old app is closed and
set `DB_FILE_NAME` to the copied file. Do not copy a live SQLite database without
its pending WAL data.

## Packaged application

Packaged builds continue to use `personal_finance.db` in Electron's writable
`userData` directory. Forge includes `drizzle/` as an extra resource, and startup
loads migrations from `process.resourcesPath`. Development paths and `.env` are
not used to choose the packaged database location.

## Verification

`pnpm test:db` runs isolated SQLite tests covering CRUD, month boundaries, category
joins, user isolation, input validation, seed idempotence, schema constraints,
legacy adoption, successive migrations, and rollback after a failed migration.
Profile tests also cover locale persistence after restart, catalog initialization,
invalid profiles, duplicate emails, and isolation between active profiles.
